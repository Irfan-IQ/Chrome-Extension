0. Methodology

How these numbers were produced.

Host

Ubuntu 22.04 LTS on a 12‑core AMD Ryzen 7 7840U workstation (16 GB DDR5). Backend hosted on an isolated Hetzner GEX44 (RTX 4000 SFF Ada 20 GB). Chrome 131 stable with a single pinned tab.

Workload

Each trial submits a fixed scripted redaction task: 300 tokens of synthetic text containing 6 PII entities (names, emails, phone, Aadhaar, PAN, address), piped through the extension’s background service worker.

Instrumentation

CPU utilisation sampled via /proc/stat at 100 ms resolution. Memory sampled via /proc/[pid]/smaps_rollup (PSS, Private_Clean + Private_Dirty). Trials isolated with 15 s cooldown; cache cleared between runs.

Dataset & Repro

30 independent trials executed back-to-back on 2026-01-15. Raw CSV in Section 7 (“Export Raw CSV”). Full harness is open-source at bench/ in the project repository.

1. Summary

Key findings from the benchmark run.

Methodology

The extension's background process was exercised across 30 independent trials. Each trial captured CPU utilisation and resident memory (PSS and Private) at three checkpoints: idle baseline, peak during workload, and post-shutdown.

Runtime Behaviour

During active workload, CPU utilisation rose from a baseline of ~3% to a mean peak of ~15.86%, with a maximum observed value of 32.92%. Transient memory allocation averaged 352 MiB above baseline. Utilisation returned to baseline immediately on completion.

Memory Reclamation

Net PSS delta between pre- and post-run states averaged +0.39 MiB, well within measurement noise. The distribution shows no monotonic growth across trials, indicating the process reclaims allocations cleanly on exit.

2. Metric Definitions

Reference for the metrics reported throughout this document.

CPU Utilisation (%)

Processor occupancy sampled at each phase of a trial: Before (idle baseline), Average (mean during workload), Peak (maximum sample during workload), and After (post-shutdown).

PSS (Proportional Set Size)

Resident memory attributed to the process, including its proportional share of pages mapped from shared libraries. Standard metric for per-process memory accounting on Linux/Android.

Private RSS

Resident pages mapped exclusively to this process, excluding any shared mappings.

Δ Peak PSS

Defined as Peak PSS − Baseline PSS. Characterises transient working-set growth during the workload.

Residual PSS

Defined as Post-run PSS − Baseline PSS. Values near zero indicate complete allocation reclamation; sustained positive drift across trials would indicate a leak.

MiB (Mebibyte)

Binary memory unit; 1 MiB = 220 bytes = 1,024 KiB.

8. Conclusion

Operational implications of the benchmark results.

Result: Within Operating Envelope

Across 30 trials, the process demonstrates stable and bounded resource usage:

  • CPU: Peak utilisation stays below 33%, with a 15.86% mean under active workload.
  • Memory: Baseline footprint sits around 670 MiB PSS. A 1,200 MiB total allocation (approximately 500 MiB headroom) comfortably accommodates the observed peak.
  • Reclamation: Residual PSS averages +0.39 MiB across trials with no monotonic drift — no leak signature.
